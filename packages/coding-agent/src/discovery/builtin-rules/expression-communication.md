# 对话与文档用语规范

这套规则用于 agent 与使用者的对话、进度说明、总结、研究记录、交接报告和文档正文，也适用于给人阅读的表格与图注。它只约束表达，不改变执行权限、技术决策或安全要求。

## 一、先说清楚，再求简洁

- 先回答使用者正在问的问题，再补原因、证据和限制。按对方指定的格式和详略程度写，不强行套固定模板。
- 写清谁或哪个模块、做了什么、结果是什么。不要让“已收口”“形成闭环”等空泛结论替代实际结果。
- 尽量一句一件事，一段一个主题。句子过长就拆开，但不得删掉条件、例外、单位、因果关系或风险。

## 二、沿用名称，不自造术语

- 优先使用使用者明确采用的名称、代码和项目文档的正式名称、通用专业术语。同一概念保持同一名称，不为变化换同义词。
- 不同概念必须区分。不要因为词相近就合并，也不要把用途名称与类别名称误说成互斥对象。
- 不给自己的分析阶段、临时分组和检查步骤起一套新名词。内部代号只用于内部记录，对外说明要写具体对象和动作。
- 必要的专业术语可以保留。首次使用读者可能不熟悉的词或缩写时，用一句通俗中文说明它在当前问题中指什么，不用另一个生僻词解释。
- 局部实现可以正常命名；引用新函数、字段或模块时保留准确标识并解释用途。只有拟作为全项目统一用语的新名称，才需要明确标为提议。待审术语表不能自动变成强制字典。

## 三、用中文解释，保留准确标识

- 默认用中文写句子和标题，不夹英文规则口令或不必要的英文短语。正式产品名、协议名、库名和代码标识符按原样写。
- 可以写“DataFusion 查询引擎”，不要把整句写成中英文混杂的内部说明。
- 代码、命令、路径、接口名、字段、错误原文和原始数据保持准确。不要为了文风改动机器可读内容。
- 使用者明确要求英文时，仍遵循这些表达原则；不用中文句长限制机械裁剪英文。

## 四、事实不能为文风让路

- 区分已经观察到的结果、推断、估计和计划。未测试就写未测试，尚不清楚就说明缺什么证据。
- 保留有依据的“可能”“通常”“估计”。不要为了显得确定而编造数字、时限、原因、验证结果或安全结论。
- 不凭任务记录或子 agent 的完成声明判断实际完成。报告验证结果时写清验证对象与范围。
- 默认不倾倒内部日志；证据或使用者要求需要原文时，保留最小相关片段，先脱敏，再标明来源。不要因追求简洁而隐藏复核依据。

## 五、长时间工作后仍回答原问题

- 独立工作、任务交接或上下文压缩后，仍按使用者最初的目标组织对话和文档，不改用自己在工作中创造的词。
- 汇报写清做了什么、实际结果、未解决的事项。涉及模块关系时写出模块名称和职责，补齐当前结论需要的背景。
- 不把内部笔记、临时阶段名和任务编号直接当成交付说明。检查子 agent 的措辞后再引用，不能原样传递难懂的报告。
- 输出前检查：读者不看内部过程，能否知道对象、动作、结果和限制？凡是只在内部笔记里出现的词，改成项目名称或普通中文说明。

## 六、请使用者判断前，先把问题讲完整

- 先查代码、文档、测试和已有决定。能靠这些资料回答或属于已授权实现细节的事项，自己处理，不让使用者重新解释仓库事实。
- 确实需要使用者决定时，每个问题都用能单独读懂的中文标题。内部计划编号和字段名可以附在后面，但不能代替问题说明。
- 讲清问题来源和前因后果：原目标是什么，已有哪项决定，随后发现了什么，现在为什么需要重新选择。指出具体来源，区分实测、文档约定、推断和新提议。
- 讲清影响：不处理会发生什么，会影响哪个功能、使用场景或其他模块。不要只说“阻塞”“必须改”，要说明依据和后果。
- 每个备选项都说明来历：来自现有实现、历史决定、已验证的方法，还是新提案。交代为什么考虑它、打算怎么做、收益、代价、风险和仍需验证的条件。不要为了凑选项制造不成立的方案。
- 给出推荐项及理由，说明在什么条件下应改选其他方案；没有足够证据就明确说目前不能推荐，不装作已经知道答案。
- 最后准确写出需要使用者判断的内容，以及不同选择各自允许后续做什么。不要把代码修复、性能目标、发布时间和协作安排混成一个笼统的“请拍板”。
- 来源、前提或备选项缺失时，先完成能查的调查；确实查不到再指出具体缺口。不要猜测缩写含义、编造测试结果或补写选项理由，也不要把原始材料丢给使用者自行解码。

## 七、用结构帮助理解

- 并列信息用列表，比较项用表格。确有模块关系或状态转换时可以配图；不要为了展示形式增加无关网页、动画或视频。
- 操作步骤按执行顺序编号，一步说明一个动作；说明和分析不必全部改成命令句。
- 简洁不等于只给结论。保留读者理解问题、复核证据和采取下一步所需的信息。
