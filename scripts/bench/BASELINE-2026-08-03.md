# Context-Maintenance E2E 基线报告（WS0）

**日期:** 2026-08-03
**方法:** 移植 DeepSeek-Reasonix `benchmarks/context-maintenance-e2e/main.go` 方法论到 omp fork
（`scripts/bench/context-maintenance-e2e.ts`），对真实 DeepSeek API 测量 omp 自身 prune 原语的行为。
**环境:** omp 17.2.5-custom · deepseek-v4-flash（api.deepseek.com）· 1M 上下文 · x64-only

## 1. 结果

### 1.1 缓存 TTL 探针（预飞行验证）

| idle 时长 | pruned 臂 hit | control 臂 hit | 结论 |
|---|---|---|---|
| 0.3 min（seed 后立即） | 88704/88834 (99.85%) | 87680/87813 (99.85%) | 缓存命中路径 + `prompt_cache_hit/miss_tokens` 字段映射 ✓ |
| 6.3 min | 88704/88834 (99.85%) | 87680/87813 (99.85%) | **5 分钟 TTL 假设不成立** |
| 16.7 min | 88832/88834 (99.998%) | 87808/87813 (99.994%) | **缓存粘性 ≥ 16.7 min**（无实际"冷重启"状态） |

**修正计划假设:** DeepSeek v4 prefix cache 不按 ~5 min 过期；实测 16.7 min idle 仍近 100% 命中。
"冷重启 miss 节约"不是 prune 的价值主张；真实价值 = **每次请求的计费体积（prompt tokens）**
（hit 价 ¥0.15/M vs input 价 ¥1.5/M，10x 价差；体积减 8.6x → 单请求成本降 ~8.6x 且延迟更低）。

### 1.2 prune 触发行为（fat 会话：20 条 × 12KB tool results ≈ 88K prompt tokens）

| 配置 | pruned | 结果 |
|---|---|---|
| 生产默认（protectTokens=40K, minimumSavings=20K） | **0/20** | 保护窗边缘（保护 ~14 条，候选 ~6 条 ≈18K est < 20K 门槛）→ **不触发** |
| 激进（protectTokens=5K, minimumSavings=2K） | **18/20** | prompt 88,834 → 10,336 tokens（**-88.4%**），cache hit 10240/10336 |

发现：omp 生产默认的 per-turn age-prune 在 88K/20-fat-result 规模会话**不触发**；要吃
prune 收益需调配置或依赖 compaction/shake 路径。

### 1.3 comprehension 探针（prune 占位符后是否幻觉）

**5/5 通过**。每轮：唯一含秘密数字的 tool result 被 prune 成占位符后，模型在工具循环中
**重新 read_file 并答对**（re_read=true, answered=true 各 5/5）。→ omp 占位符 prune 不引起幻觉。

### 1.4 成本折算（按 models.yml deepseek-v4-flash 价：input 1.5 / output 6 / cacheRead 0.15 ¥/M）

| 场景 | 每请求 prompt 计费（hit 价） | 相对 |
|---|---|---|
| 默认配置（prune 未触发） | 88.8K × ¥0.15/M ≈ ¥0.0133 | 1x |
| 激进 prune 后 | 10.3K × ¥0.15/M ≈ ¥0.0016 | **0.11x** |

## 2. 对 WS1 决策的影响（数据驱动）

| 维度 | 数据 | 结论 |
|---|---|---|
| 成本侧（钉住保留的 token） | 缓存粘性 + hit 价 ¥0.15/M → 钉住 1500 tokens ≈ ¥0.0002/turn | **成本可忽略** |
| 收益侧（约束保真） | 本次只测了"tool result 丢失"（5/5 不幻觉）；**"user 约束被 summarize 稀释"未直接测量** | 需补充探针（见下） |
| 策略取舍（#3174 vs Reasonix prune-skip） | 粘性缓存下两者缓存收益差异趋零；prune 的价值是体积控制而非 miss 避免 | **维持 omp 现状（#3174 锚定 billed tokens），不采纳 Reasonix 跳过语义** |

**建议：实施 WS1**。理由：成本侧已实证可忽略（粘性缓存 + hit 计价），收益侧是保真
（用户硬约束不因 compaction 丢失），值得。实施顺序：
1. 先补一个约束稀释探针（WS1 首任务）：会话中 user 声明硬约束 → 触发 compaction → 问约束内容，
   量化"进 summary vs 逐字保留"的保真差（预期 summary 有损）；
2. 按探针结果选变体：B（折叠区小 turn 自动钉住，配总量上限）为主，C（`[[keep]]` 用户标记）为辅；
3. provider-native compaction（OpenAI replay）路径的 preserveData 接合按计划 §3.2 执行。

## 3. 附带发现

- `omp -p` headless 路径可用（`--resume`/`--print`/`--approval-mode`/`--api-key`），为真实 agent 路径
  基准预留。
- DeepSeek thinking 模式多轮必须回传 `reasoning_content`（空串可），否则 400——omp provider 层
  已处理，基准脚本同步处理。
- omp prune 的 idle-flush（30 min）在粘性缓存世界基本无用，但无害。

## 5. WS1 约束稀释探针（2026-08-03，`scripts/bench/constraint-dilution.ts`）

**问题:** compaction 折叠后，用户硬约束（"NEVER 裸 cargo build" + 唯一口令）在 summary 里是否保真？
**方法:** 62 条消息会话（约束 turn 置于折叠区中部），用真实 `prepareCompaction`+`compact`（注入
`completeImpl` 直连 DeepSeek），control 臂=当前行为（约束进 summary），treatment 臂=钉住逐字保留；
问答要求逐字复述约束与口令。

| 探针 | control（summary-only） | treatment（钉住） |
|---|---|---|
| 单轮 compaction（5 trials） | **5/5** 逐字复述成功 | 5/5 |
| 3 轮连续 compaction 漂移（3 trials，marker 每轮检查 + 终问答） | **3/3**，marker 每轮存活 | — |

**结论（数据驱动，措辞收敛）:**
- 当前 compaction 提示词 + deepseek-v4-flash 下**未观测到约束稀释**（trials 有限、单模型单任务形态；
  换模型/提示词后可能重现——这正是探针保留为回归工具的原因）。
- omp 的 compaction-summary / update-summary 提示词已显式要求"硬性规则/路径/数字逐字保留"
  （`compaction-summary.md` 与 Reasonix `summarySystemPrompt` 的 Standing facts 段同源），
  实测约束跨 3 轮折叠无漂移。
- **WS1 变体 A/B 关闭**（边际收益证据不足）；变体 C（`[[keep]]` 标记）降级为 WS4 备选。
- 本探针转为 compaction 提示词回归工具：提示词改动后重跑防漂移回归。
